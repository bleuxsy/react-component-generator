# Commit

작업 트리의 변경사항을 분석해 컨벤션에 맞는 커밋을 만든다.

## 실행 모드

| 모드 | 진입 조건 | 동작 |
|---|---|---|
| **승인 모드** (기본) | 아래 조건이 없을 때 | Step 4에서 계획을 보여주고 승인 후 커밋 |
| **자동 모드** | 인자에 `--auto`가 있거나, 사용자가 "바로 커밋해줘", "승인 없이", "묻지 말고 커밋" 등으로 명시 | Step 4의 승인 대기를 건너뛰고 바로 커밋 |

자동 모드 판단이 애매하면 승인 모드로 동작한다. 자동 모드는 해당 호출에만 적용되며 다음 호출로 이어지지 않는다.

자동 모드에서도 다음 안전장치는 그대로 유지한다.

- Step 1의 제외 대상(비밀 정보·산출물 등)은 자동으로 제외하고 보고만 한다. 자동 모드라도 포함시키지 않는다.
- 아래 상황에서는 자동 모드를 중단하고 승인 모드로 전환해 사용자에게 묻는다.
  - 제외 대상인지 판단이 애매한 파일이 있을 때
  - 이미 staged된 파일과 unstaged 변경이 함께 있어 범위가 불분명할 때
  - pre-commit 훅이 실패했을 때

## Step 1. 변경사항 수집

다음을 실행해 현재 상태를 파악한다 (독립 명령은 병렬 실행).

```bash
git status --short
git diff              # unstaged 변경
git diff --staged     # staged 변경
git log --oneline -10 # 기존 메시지 스타일 참고
```

- 추적되지 않은 파일(`??`)도 대상에 포함하되, 내용을 직접 읽어 무엇인지 확인한다.
- 변경사항이 없으면 "커밋할 변경사항이 없습니다"라고 알리고 종료한다.
- 이미 staged된 파일이 있으면, 사용자가 의도적으로 고른 것일 수 있으므로 그 범위를 우선 존중하고 나머지를 포함할지 묻는다.

### 커밋하면 안 되는 파일 점검

다음이 보이면 커밋 대상에서 제외하고 사용자에게 알린다.

- 비밀 정보: `.env`, `*.pem`, `*.key`, 자격증명·토큰이 포함된 파일
- 빌드 산출물·의존성: `dist/`, `build/`, `node_modules/`, 캐시 파일
- 대용량 바이너리, 개인 설정 파일(`settings.local.json` 등)

`.gitignore`에 추가가 필요해 보이면 제안만 하고 임의로 수정하지 않는다.

## Step 2. 논리적 단위로 분류

변경을 "하나의 목적" 단위로 묶는다. 판단 기준:

- 같은 기능/버그 수정을 위한 변경은 파일이 달라도 한 커밋
- 기능 추가와 무관한 리팩터링, 설정 변경, 포맷팅은 분리
- 의존성 변경(`package.json` + lock 파일)은 함께 묶음
- 분리하면 개별 커밋이 빌드/동작 불가 상태가 되는 경우에는 묶음

한 파일 안에 서로 다른 목적의 변경이 섞여 있으면, 무리하게 hunk 단위로 쪼개지 말고(대화형 `git add -p`는 사용할 수 없음) 해당 파일이 주로 속한 단위에 넣고 그 사실을 계획에 명시한다.

## Step 3. 커밋 메시지 작성

형식:

```
<type>: <한국어 요약>

- (선택) 변경 이유나 세부 내용
```

| type | 사용 시점 |
|---|---|
| `feat` | 새 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 코드 구조 개선 |
| `chore` | 빌드·설정·의존성·문서 등 기타 작업 |

규칙:

- 요약은 한국어로 50자 이내, 마침표 없이, "~추가", "~수정"처럼 명사형/간결체로 끝낸다.
  - 예: `feat: 컴포넌트 미리보기 패널 추가`, `fix: 빈 프롬프트 제출 시 오류 수정`
- "무엇을"보다 "왜"가 diff만으로 드러나지 않으면 본문에 적는다.
- 위 4개 type에 맞지 않는 경우 가장 가까운 것을 고르고, 애매하면 `chore`를 쓴다.
- 대화에 커밋 attribution 지침(예: `Co-Authored-By` 트레일러)이 있으면 메시지 끝에 따른다.

## Step 4. 계획 제시 및 승인

> **자동 모드**: 아래 계획을 출력만 하고 승인을 기다리지 않고 바로 Step 5로 진행한다 (마지막 "이대로 커밋할까요?" 문구는 생략).

승인 모드에서는 커밋 전 아래 형식으로 계획을 보여주고 승인을 요청한다.

```
커밋 계획 (총 N개)

1) feat: 컴포넌트 미리보기 패널 추가
   - src/components/Preview.tsx
   - src/App.tsx

2) chore: eslint 설정 추가
   - eslint.config.js

제외: .env (비밀 정보 의심)

이대로 커밋할까요? (수정할 부분이 있으면 알려주세요)
```

- 사용자가 수정을 요청하면 계획을 고쳐 다시 보여주고 재승인을 받는다.
- 명시적 승인("응", "좋아", "진행해" 등)이 있을 때만 Step 5로 간다.

## Step 5. 커밋 실행

계획 순서대로 커밋마다:

```bash
git add -- <해당 파일들>
git commit -m "<메시지>"
```

- `git add .`/`git add -A`는 쓰지 않고 파일을 명시한다 (제외 파일이 섞이는 것을 방지).
- 여러 줄 메시지는 heredoc(Bash) 또는 here-string(PowerShell)으로 전달한다.
- pre-commit 훅이 실패하면 `--no-verify`로 우회하지 말고, 원인을 보고하고 수정 여부를 묻는다. 훅 실패 시 커밋은 생성되지 않았으므로 `--amend`가 아닌 새 커밋으로 재시도한다.
- 현재 브랜치가 기본 브랜치(main/master)면 커밋 전에 그 사실을 알려준다. 브랜치 생성은 사용자가 원할 때만 한다.

## Step 6. 결과 보고

```bash
git log --oneline -<N>
git status --short
```

생성된 커밋 목록과 남은 변경사항(있다면)을 보고한다. **push는 사용자가 별도로 요청할 때만 한다.**
