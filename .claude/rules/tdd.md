# TDD Rule

> **경고: 이 규칙은 Rigid다. 상황에 맞게 변형하지 마라.** 적용 대상이면 예외 없이 아래 사이클을 따른다.

## 0. 우선순위

- 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 프로젝트 규칙이 없을 때 쓰는 **기본값(fallback)**이다.
- 테스트 실행 명령은 프로젝트 문서에 적힌 것을 쓴다 (이 저장소: `bun run test`).

## 1. 적용 기준

**TDD 필수**
- 비즈니스 로직 (도메인 규칙, 상태 전이, 계산)
- API (엔드포인트, 요청 검증, 에러 매핑, 응답 형식)
- 유틸리티 / 순수 함수 (파싱, 변환, 정규화)
- 버그 수정 (**버그를 재현하는 실패 테스트부터** 작성)
- 사용자 입력에 따라 분기하는 UI 동작 (활성/비활성, 제출 가드 등)

**TDD 불필요**
- 타입 정의, 인터페이스
- 설정 파일 (빌드, 린트, tsconfig, 환경 변수)
- 동작 없는 순수 UI (마크업, 스타일, 문구, 레이아웃)
- SQL 스키마 / 마이그레이션 정의
- 문서

판단이 애매하면 **적용 대상으로 간주**한다.

## 2. RED-GREEN-REFACTOR

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에서 여러 동작을 검증하지 마라.
- 테스트 이름은 기대 동작을 서술한다.
- **반드시 실행해서 실패를 눈으로 확인**한다. 실행하지 않은 RED는 RED가 아니다.
- 실패 이유가 **"기능 미구현"**이어야 한다 (기대값 불일치, 함수 없음 등).
  - 문법 오류, import 경로 오류, 테스트 설정 오류로 인한 실패는 RED가 아니다. 고치고 다시 실행한다.
- 작성 즉시 통과하면 테스트가 잘못되었거나 이미 구현된 동작이다. 테스트를 재검토한다.

### GREEN: 통과시키는 최소 코드

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI**: 테스트가 요구하지 않는 분기, 옵션, 일반화, 에러 처리를 추가하지 마라.
- **신규 테스트 + 기존 테스트 전체가 통과**하는지 실행해 확인한다.
- 기존 테스트가 깨지면 GREEN이 아니다. 테스트를 수정하지 말고 구현을 고친다 (요구사항이 바뀐 경우만 예외).

### REFACTOR: 동작 유지하며 정리

- 허용: 중복 제거, 이름 개선, 헬퍼 추출, 구조 정리.
- **매 변경 후 테스트를 실행해 green을 유지**한다.
- **새 동작 추가 금지.** 새 동작이 필요하면 다음 RED로 넘긴다.
- 정리할 것이 없으면 건너뛴다.

### 반복

- 다음 동작을 골라 **RED로 돌아간다.**
- 모든 동작이 끝나면 전체 테스트와 린트를 실행하고 종료한다.

## 3. 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성했다면 **그 코드를 삭제하고 RED부터 재시작**한다.
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 클립보드 메모 모두 해당한다.
- 삭제 후 테스트를 쓰고, 테스트가 요구하는 만큼만 다시 구현한다.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트 불필요" | 단순하면 테스트도 1분이면 끝난다. 단순한 코드가 깨질 때가 가장 발견하기 어렵다. |
| "나중에 추가하겠다" | 나중은 오지 않는다. 구현 후 작성한 테스트는 코드에 맞춰진 확인용일 뿐, 설계를 이끌지 못한다. |
| "시간이 없다" | 디버깅과 회귀 수정이 더 오래 걸린다. 시간이 없을수록 TDD로 재작업을 줄인다. |
| "삭제하면 낭비" | 매몰 비용이다. 테스트 없이 쓴 코드는 검증되지 않은 부채이며, 다시 쓰는 것이 더 빠르고 정확하다. |
| "프로토타입이다" | 프로토타입은 대부분 그대로 프로덕션이 된다. 정말 버릴 코드라면 적용 대상 코드베이스에 두지 마라. |
